# 逐笔转分钟交错并行校验提示词

更新日期：2026-10-22。适用于所有通过本框架生成的单表、双表或三表分钟指标，
不绑定具体研究主题、指标数、日期范围或并行数。

交错执行仅用于新数据首次历史全量构建；每日增量按“生成→发布→本次范围校验”
顺序执行，不启动交错校验队列。其他日期范围、快照、来源和校验等级要求仍适用。
全量转日更入口及未来统一调度约定见[标准流程](历史全量转每日增量标准流程.md)和
[调度接入约定](统一日更调度接入约定.md)。1.2.0标准入口本身采用顺序校验，首次
全量的交错编排仍需业务另行实现，不能因使用新入口就宣称已支持动态校验队列。

本文件是可直接交给执行人员或AI的通用要求。框架现有能力包括月文件原子发布、
逐指标manifest及逐日`source_contracts`；动态校验队列、校验断点和资源协调须核对
业务校验入口的实际实现。本文件不表示这些调度能力已成为核心内置API，也不把
某个业务脚本的参数当作通用公开接口。本节描述交错校验要求，不改变分钟计算逻辑。

## 可直接复制的提示词

```text
请为当前逐笔转分钟数据任务组织高效、可恢复的生产输出校验。仅首次全量允许生成后续日期
与校验已正式发布的日期交错执行；以已提交的发布检查点为准，不等待整个生成
任务先变为complete。采用有界并行，并在相同校验口径下记录实际效率。

一、先核对任务及实际能力

1. 完整读取框架和任务根目录的AGENTS、README、CHANGELOG、本业务README及
   generation_spec.json；读取最新三表任务书、分钟消费交接规范和统一契约。
   核对当前适配器、执行器、发布机制、业务校验入口及相关测试；不要猜接口名。
2. 列出每项指标的输入表和字段、公式、事件或订单统计单位、关联键与基数、方向、
   时间锚点、股票全集、值类型、空值与真空分钟语义、输出路径和算法契约。
   任务目录使用与生产主题目录一致的英文名；生产仍为每指标独立四列月Parquet。
3. 分别核对源码、实际导入/安装、逐日输入及历史分钟结果。正式业务要求报价3，
   核对实际source_contract门禁、物理Schema/缩放和成功源质检；升级代码不证明
   已有输出采用新口径。旧/未知来源不得补造凭证或自动重建。
4. 确认校验器是否支持动态已发布范围、稳定文件读取、独立校验检查点及并行参数。
   缺失能力时先说明并在授权范围内补齐、验证；仅修改提示词不能宣称能力已实现。
   不能简单删除manifest的complete检查后直接启动并发读写。

二、冻结增量范围，防止误校验全部历史

5. 将本次授权指标、日期及生成run_id保存为独立校验范围清单。默认范围是本次
   实际新增或重算的“指标×日期”，通常取已核实属于本次运行的各指标
   manifest.pending_dates与用户日期区间的交集，再合入同一授权任务遗留的未
   校验发布日期。本次run_id须由可信任务记录或经核实的本次生成清单确认。
   当前执行器有待计算日期时，启动只在内存创建running清单，不立即写manifest；
   首次发布检查点提交前，路径中的manifest可能不存在或仍属于旧run_id。尚未
   确认本次清单时保持等待范围确认，不能沿用旧pending_dates或旧complete状态。
   缺少可靠范围记录时按第6条处理。首次构建可以覆盖全部目标日期；已有历史
   不能只因起止日期较宽就自动进入范围。
6. manifest只记录最近一次运行。生成续跑可能换run_id和pending_dates，不能用
   最新清单覆盖原校验范围、漏掉前一运行已发布但尚未校验的日期，也不能任意
   扩大范围。缺少可靠范围记录时明确报错或请求补充，不退回历史全量扫描。
   全量校验须由用户明确要求并显式开启；禁止轮询时反复扫描全部历史业务数据。
7. 尚未提交匹配发布检查点的目标记录为等待发布，即使正式文件已存在也不能
   直接入队；不能因暂时缺文件就报漏日。生成结束后仍未满足发布条件的目标
   报告未完成/失败：区分文件缺失与文件存在但发布凭证未确认，不自动补造
   检查点。区间内确实没有本次目标时标记无任务，不将其表述成校验通过。
8. 源口径或算法变化时，逐项核对受影响的指标×日期，列出已授权重建与尚未重建
   范围。不能只校验新日期或曾报错的指标后宣称所有历史结果已适配。

三、以发布检查点衔接生成与校验

9. 生成和校验独立推进。校验队列只接收目标范围内已原子发布、发布检查点及
   footer来源契约一致的指标×日期。生成状态为running时，也可以校验其已提交
   月份；computed进度、日志显示算完、暂存分片或文件存在都不等于发布成功。
10. 按月批量接收新发布结果，不为校验改变生产月文件结构或擅自增加发布频率。
    逐指标确认就绪：组内多项月文件依次发布，整个指标组不是跨文件原子事务，
    不能因一个指标发布就认定同组其他指标或三张源表也已全部就绪。
    当前组执行器须等当月待发布批次全部成功返回后，才更新各指标发布进度并
    依次写manifest；并非每项文件替换后立即提交其检查点，manifest更新也不是
    跨指标事务。若后项发布失败，前项文件可能已替换但没有该月检查点，仍按
    第7条处理，不能仅凭文件或footer推定本次发布已确认。
    文件替换与manifest更新之间的等待没有固定短时上限：默认异步模式可能
    先完成下一整月计算，再收取上一月发布结果并提交检查点；下一月计算失败
    时，上一月已替换的文件也可能尚未记入检查点。等待期间持续核对本次运行
    和目标版本，不使用固定短超时直接判漏日，也不擅自补写生成manifest。
11. 固定每批读取的输出版本及输入身份。优先使用一个保持打开的文件对象贯穿
    footer和数据读取，或使用经确认的不可变快照；同一批多次按路径重新打开
    可能读到不同版本。只读快照若需落盘，放校验工作区并记录清理，不改生产。
12. 校验前后检查来源与发布版本。输入变化、目标日期被重算或校验口径变化时，
    该项结果标记为失效并重新排队；不把竞争窗口误报为稳定结果。
    同月仅新增其他日期时，只有能证明原目标日期内容及契约未变才复用结论，
    否则重校受影响目标日期，不因此扫描全部历史。结束前再核对当前生产版本。
13. 生成失败时保存已通过的版本化结果并报告整体未完成；校验失败时停止派发
    对应失败分支并报告。校验不得自行终止或覆盖生成任务，也不能忽略失败后
    宣布全任务通过。是否继续其他独立分支按任务授权和错误范围决定。

四、共享I/O与有限内存读取

14. 按完全相同的物理输入表集合划分校验I/O组，再按不同关联、事件/订单、方向
    和股票全集口径拆计算分支。每个校验批次内，同一组每张物理表每交易日只
    读取一次所需字段并集，共享股票签名、数量统计及参考计算的必要中间量。
    使用按输入身份缓存和同一任务只派发一次的机制，防止并行指标各自重读。
15. 输入基准由逐笔表或独立来源凭证建立，不能从待校验输出反推，否则漏股票
    可能自洽通过。多表指标按其声明的股票并集/关联及过滤规则计算预期范围。
    缓存绑定物理来源、日期、字段和口径；来源变化即失效，不能只按日期复用。
16. 生成与独立校验是两个读取阶段，应分别统计I/O次数。若复用生成阶段的小型
    统计，明确它只能减少结构校验读取，不能代替独立业务参考结果。
17. 只定位目标日期所在的YYYY/YYYYMM.parquet，裁剪必要列。比较按交易日谓词
    与按月/行组分批一次读取的成本，依据实际行组统计和内存选择；支持跨日期
    行组，不能假定一个行组就是一天。禁止整段多年载入、反复整月全读后按日筛选，
    或为独立指标改成生产宽表/每日Parquet。
18. 在已发布的小批次内完成“输入基准→相关指标校验→检查点”，不要先串行扫完
    所有数据集的全部目标输入才开始检查输出。及时释放逐笔表与分钟大表；小型
    签名缓存可保留，较大缓存须有容量限制和回收机制。

五、并行与效率验证

19. 分别控制输入基准读取、指标/日期校验及Arrow内部线程数，并约束各阶段和
    生成任务的合计资源；多个并行数不能简单相乘后无限启动任务。
    在业务入口暴露实际可用参数，文档中的参数名不代表框架已有同名API。
20. 先用覆盖不同输入体积、市场、月份及业务分支的代表性样本，比较串行与若干
    并行档位。串并行结果、NULL位置及覆盖必须一致；交替测试或复测暖缓存，
    记录墙钟、内存峰值和磁盘吞吐，注明其他任务干扰，选择实测收益合理的档位。
21. 根据当前可用CPU、内存/cgroup、每worker实测峰值、生成负载和磁盘吞吐设置
    有界队列及并发。交错运行优先保障生成；发现内存压力或I/O争抢时减少后续
    校验派发、降低并行或等待。不要擅自取消资源限制，也不自动kill生成进程。
22. 同时限制正在计算和等待结果的任务，避免慢任务后积压大量已解码DataFrame。
    不因服务器内存大就固定最大worker数；并行不能改变公式、删缺价事件或扩大范围。

六、校验项目与断点

23. 每项输出检查独立目录、非空README、发布与来源凭证、精确四列和物理类型、
    日期、完整股票集合、唯一键，以及每股票每日242个准确的结束标签和时区。
    不能只数242行或242个不同分钟而漏掉错误标签。值域、NaN/NULL、Inf、整数
    范围和空分钟处理按该指标规格判断，不套用某个指标的固定范围。
24. 对代表性真实日期和必要边界构建独立参考公式。委托完整订单用全日或完整
    股票分区先按完整键聚合后归分钟；最早锚点、一次计单、片段量及已知额一致。
    成交保留每笔真实事件与主动方向，参与订单侧别另算；撤单保留各次事件时间。
    缺价不删除，单数/量/锚点使用完整合格输入，仅金额分支跳过空额；混合价累计
    已知部分，全缺价有事件为NULL，已知零和真无事件分别验证。
    非空负额/Inf不能静默过滤。参考公式不调用生产聚合函数，并说明共享读取或
    分钟映射的独立性边界；结构检查或小样本通过不能冒充全量逐值复算。
25. 校验状态独立保存在本业务logs/reports等工作区，不写回生产Parquet或伪造
    生成manifest。按指标×日期记录待发布、待校验、校验中、通过、失败、失效，
    绑定输入来源契约、输出快照身份、算法及校验器版本、校验等级和实际覆盖。
    检查点原子写入；崩溃后校验中的记录重入队，只有完整成功的记录可以复用。
26. 恢复时重核身份，只读取尚未通过或已失效的目标项。日志进度不是检查点，
    样本通过不能替代全股票通过，结构等级不能替代公式等级。若现有入口只有
    最新manifest日期筛选而没有校验断点，应如实说明并补齐后再称支持断点校验。

七、测试、执行和交付

27. 在授权范围内修改代码时，同步业务README和generation_spec，完成语法、中文
    和针对性pytest。必要回归覆盖：串并行一致、每表每日只读一次、running时
    已发布/未发布区分、部分指标发布、月替换竞争、源变化失效、断点恢复、空
    增量不扫描、漏日/漏股票/错误分钟确实失败。各业务用独立pytest进程并核对
    实际导入位置；不要混装同名业务包或只跑unittest遗漏函数测试。
28. 使用所属项目的执行环境，远程操作遵循AGENTS及本次已授权范围。上传后核对
    文件、运行Python语法检查及小范围真实试跑。正式运行保存PID、范围清单、
    参数、日志、检查点、开始结束时间和退出码；仅向任务工作区写审计结果。
29. 只有生成已成功结束、所有授权目标均正式发布、当前版本的全部所需校验均
    通过，且没有等待、失败或失效项，才能宣布整体完成。退出码0、进程消失、
    日志出现某项通过，均不能单独证明全任务完成。最后做目标集合对账，不因
    对账再次读取全部历史业务列；缺项报告失败。
30. 汇报逐指标目标/已发布/已通过/失败/失效数、校验等级、资源及并行变化、总
    墙钟、各阶段耗时、每个不同交易日的吞吐、读取次数与脚本/日志/结果位置。
    可另列指标×日期吞吐，但与交易日吞吐分开。阶段并行耗时不能求和当墙钟。
    加速比以相同数据和覆盖等级的基线计算，样本输入阶段与整段校验分开报告。
```

## 框架中的执行依据

- [README：输出与发布契约](../README.md)：manifest是最近一次运行清单，发布按月
  原子替换，组内指标独立发布，不能当作跨指标事务。
- [逐笔三表到分钟统一契约](逐笔三表到分钟统一契约.md)：来源、算法、事件/订单、
  NULL及历史重建边界。业务逐项提供独立参考结果。
- `trans_to_min/storage.py`的月发布先检查临时文件再替换正式文件；
  `runner.py`收取成功发布结果后更新`months`和检查点进度；`group_runner.py`
  等当月待发布批次全部成功返回后再更新发布进度，随后依次写各指标manifest。
  文件替换和manifest提交不是同一个原子事务，后项失败可能留下未确认的前项文件。
- 有待计算日期时，执行器不在启动时立即写running manifest；正常首次落盘发生
  在首个发布检查点提交时。无待计算日期的恢复任务直接写complete，失败路径写
  failed。默认异步发布的检查点可能等到下一整月计算结束；最后一月在循环结束
  收取。校验不能假设启动即有本次清单或文件替换后马上有检查点。
- `trans_to_min/provenance.py`通过实际输入身份、元数据、核心/业务源码和算法参数
  构建逐日契约；月footer保存`source_contracts`，计算期间源变化会拒绝发布。
  这些契约不是输出内容摘要，不能单凭契约相等证明同月替换后的目标日期值未变。
- 按月增量可能替换同一个正式路径。校验实现必须固定快照并核对版本，不能把
  `os.replace`的单次原子性理解成多次读取自动获得相同文件。

本提示词要求的动态队列、校验检查点与资源协调应由相应业务校验入口或外部编排
实现，具体公式留在业务目录。文档落地不代表已有业务入口已经支持交错校验。
