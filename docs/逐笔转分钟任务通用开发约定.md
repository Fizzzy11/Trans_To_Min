# 逐笔转分钟任务通用开发约定

适用于所有基于 Trans_To_Min 的分钟数据任务，与具体指标无关。来源是 2026-11 对七个已有任务
（四项基础分钟、entropy、maxdiv、time_center）的代码检查、提速和框架 1.2.2→1.4.0 升级中
反复遇到的问题。每条约定后面写了原因，原因不成立时可以不照做。

具体的数据事实（三表排序、物理类型、规模、磁盘吞吐）和实测数字见
[逐笔转分钟业务开发必读](逐笔转分钟业务开发必读.md)，本文不重复，只写可推广的做法。
本文是开发约定，不改变框架行为。2.0.0起其中计算、运行、校验方面的多条已由框架直接实现或强制，
写法见[2.0.0发布说明](发布说明_2.0.0.md)；条目里注明“2.0.0起由框架…”的，照框架做即可。

## 一、开工前

1. **先写清口径再写代码。** 每个指标列出：输入表、用到的字段、事件归哪一分钟、股票全集、
   无事件与缺值分别输出什么、输出类型。
   原因：检查中发现的口径分歧几乎都出在“无事件”和“有事件但缺价”没有事先区分。
2. **先用一个真实交易日测量，再设计并行和调度。** 记录单日耗时、单进程峰值内存、读入行数。
   选近年的大日，不要选早年的小日。
   原因：早年数据量约为近年的三分之一，按小日估算会在全量跑到近年时内存不够。
3. **按“读同一组物理表”划分任务组。** 读同一张表的指标放在同一个组里一次读入、一起算。
   原因：全量的下限由读盘总字节决定，同一张表读两遍就是两倍时间。

## 二、读数

4. **业务代码不按路径打开逐笔源文件。** 生产公式只用执行器给的 `inputs`，独立参考只用
   `sources[dataset].open()`。
   原因：框架保证每个源文件只读盘一次并在任务间共享，自己另开一条读盘路径会破坏这一点。
5. **只声明公式真正用到的字段。**
   原因：每声明一个字段就是一整列内存，亿级行下一列就是 1~2G；有些派生字段（如物理表没有的
   金额）会对全日数据整列计算。
6. **对数据的任何假设都要先检查、不成立时走回退路径。** 典型的是“源文件按股票和时间有序”。
   原因：假设成立时能快几倍，但不检查就使用，一旦某天不成立会静默算错。
7. **不原地修改执行器给的输入表。** 需要变换时先复制需要的列。
   原因：输入表在组内各指标间共享，改了会影响其他指标；框架对部分列已设只读，会直接报错。

## 三、计算

8. **亿级行不写逐行或逐分钟的 Python 回调，也不用 pandas 计算。** 2.0.0起计算只写在
   `BlockMetricGroup.compute_block`里，只用numpy与`trans_to_min.kernels`；所在模块导入pandas
   框架直接报错。
9. **用“有序分段归约”，不用哈希分组。** 块内“股票×分钟”格键已非降序，直接用`kernels.sum_by`
   等函数；按订单号等无序键归约用`kernels.group`。
   原因：实测比多次 `groupby` 快 4~8 倍；每次 `groupby` 都要重新对键做哈希。
10. **去重计数用`kernels.distinct_count_by`（打包成单个整数后排序、数相邻变化），不用哈希去重。**
    原因：近似有序的数据上排序接近线性，实测比 `pd.unique` 快数倍。
11. **整数量在整数域求和，并检测溢出。** 不用 float64 累加数量。
    原因：uint64 溢出是静默回绕，float64 超过 2^53 会失真，两种错都不会报错。
12. **金额一类的浮点求和要明确精度方案，并固定下来。** 需要精确时在物理整数域求和后再除
    scale：2.0.1起用`kernels.raw_integers`按`block.field_info`无损还原原始整数，不假设scale，
    也不自行读footer；用浮点时选定一种求和方式（带补偿或不带），不要混用，也不要依赖 `np.longdouble`。
    原因：不同求和方式末位不同；`longdouble` 在 Linux 和 Windows 上精度不一样。
13. **区分三种状态并分别测试：无事件、有事件但值缺失、值为零。** 分支求和时只把选中的行
    送进去，不用 0 占位。
    原因：用 0 占位会把“缺失”变成“零”，带补偿的求和加 0 还会改变末位。
14. **取子集时按列取 numpy 数组再用掩码，不整表 `loc`/`iloc` 复制。**
    原因：整表复制在亿级行上既慢又让内存翻倍。
15. **全量、日更、重算共用同一套指标实现**，只通过日期清单区分。
    原因：复制两套公式迟早会改了一套忘了另一套。

## 四、测试

16. **至少有一组测试走“真实 Parquet 文件 → 适配器 → 业务”的完整链路。**
    原因：直接构造 DataFrame 的测试绕过了适配器，证明不了生产链路能拦住非法值；检查中还发现
    过业务层的检查分支在真实链路上根本到不了。
17. **边界用例固定要有：** 全日只有一条事件、整分钟全部缺值、仅盘后出现的股票、
    15:00:00 整点、同一毫秒多条、数量接近整数上限。
18. **测试只依赖框架的公开接口，不模拟框架内部函数的签名。**
    原因：三个旧任务各有测试因为模拟的内部读函数少了一个参数而长期失败，一直被当作“已知失败”
    带着走，掩盖了后来的真实失败。
19. **交付时测试全部通过；有已知失败就修掉或删掉，不留。** 在服务器（Linux）上跑一遍为准。
    原因：有的测试依赖文件时间戳精度，Windows 上偶发失败、Linux 上不出现。
20. **提速或重构后，先在少量真实日期上与旧结果逐位比对，再谈推广。** 报告里写清是
    “逐位相同”还是“容差内一致”，两者不能混称。

## 五、校验

21. **校验默认从轻。** 2.0.0起框架默认`light`：全部日期结构检查，加最多3个代表日的全股票
    独立复算；全部日期逐值复算（`full`）只在首次上线或公式改动后的小范围内做，并须说明理由。
    原因：全部日期逐值校验等于把指标再算一遍，CPU 和内存开销接近翻倍；生成本身已经很耗时。
22. **校验等级如实声明并写进报告。** 抽样就写抽样了哪些日期和股票，不能把结构检查写成
    公式校验通过。
23. **独立参考用和生产不同的算法写**（例如生产用打包排序，参考用 lexsort）。
    原因：同一套算法算两遍只能发现偶发错误，发现不了公式理解错误。
24. **校验不重读源文件。** 参考值在生成时用同一份已读入的源数据顺带算出，校验只比对结果。

## 六、运行

25. **全量开跑前代码定版。** 中途改了公式，要自己对受影响日期显式重算。
    原因：框架 1.4.0 起不记录任何版本或来源凭证，已发布日期一律视为可信并跳过，不会提醒。
26. **分三步放量：1~3 天 → 一个月 → 全量。** 每一步核对结果、耗时和峰值内存后再进下一步。
27. **并行度、线程数和内存分配交给框架。** 2.0.0起用`python -m trans_to_min run`启动，框架按实测
    内存反推并行度、派发前读实际可用内存、超预算只暂停派发；任务只能调低`memory_fraction`。
    原因：服务器是共享的，其他人的进程随时占用内存和磁盘；各任务自建调度既重复又容易出错。
28. **任务内不写任何调度、进程并行代码**（`subprocess`、`multiprocessing`、`ProcessPoolExecutor`）。
    跨月、跨任务的派发与同表任务对齐读盘都由框架入口完成。
    原因：同一主题的清单文件并发写会冲突；检查中自建控制器多达近千行，且绕开了框架约束。
29. **日期来自明确的清单或上游成功记录，不扫描目录猜交易日，不静默跳过缺源日期。**
30. **迁移、一次性修复脚本放在任务目录之外，用完归档。** 任务目录只保留指标包、文档、测试与
    运行配置（目录规定见2.0.0发布说明）。
    原因：检查中多次遇到已执行完的一次性工具仍被测试覆盖、仍引用已删除的框架接口。
31. **不动别人的进程和数据。**

## 七、收尾与文档

32. **批次结束后清掉所有中间数据**（内存盘暂存、参考检查点、锁、试跑目录），输出目录只留
    分钟数据本身，并实际列目录确认。
33. **输出写到与源数据不同的磁盘。**
34. **README 只描述当前行为。** 行为变了就改原文或删掉旧段落，不在后面追加“补充说明”。
    原因：旧任务的 README 里新旧说法并存（例如仍写着“凭证不匹配拒绝续跑”），读的人无法判断
    哪句有效，只能再加一条“以本条为准”。
35. **报告区分“已实现、已部署、已生成、已校验”四种状态，各自给出证据。** 源码改了不等于
    服务器已部署，生成成功不等于校验通过。
36. **框架升级时，全仓搜索被删除或改名的接口**，包括业务任务的脚本、校验器和测试，以及
    残留的构建产物（如 `build/lib`）。
    原因：1.4.0 删除凭证接口后，有验收脚本仍在导入已删函数，直到评审才发现。
37. **不复制、不修改、不给框架打补丁；框架缺能力就写需求并停下来问用户。** 在任务的
    `docs/框架需求_<日期>.md`写清需求、原因与影响。
    原因：检查中有任务私改了一份框架副本自用，产出版本号带私有后缀，公共框架的修正与约束都不再生效。
38. **不自建凭证、审批、复用证明、来源身份映射一类的管控。** 已发布数据默认可信，重建用
    repair模式显式重算。
    原因：这类管控曾让一次全量因“来源身份与验收映射不同”拒绝启动，排查与维护成本远大于收益。

## 交付前自查

- [ ] 口径表写清，三种空值状态有测试；
- [ ] 没有自行打开源文件的代码，只声明了必要字段；
- [ ] 用到的数据假设都有检查和回退；
- [ ] 整数求和有溢出检测，浮点求和方式已固定；
- [ ] 有走真实 Parquet + 适配器的测试，服务器上测试全部通过；
- [ ] 大日实测过耗时和峰值内存；
- [ ] 校验等级如实声明；
- [ ] 计算只在`compute_block`里用numpy与kernels，没有pandas、没有自建调度与管控、没有框架副本；
- [ ] bench达标，`scripts/audit_task.py`检查通过；
- [ ] 中间数据已清，README 与当前行为一致。
