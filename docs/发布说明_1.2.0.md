# Trans_To_Min 1.2.0 发布说明

功能版本记录日期：2026-10-22。正式发布日期：2026-10-29。

本次新增“历史全量→每日增量”的标准流程、单指标任务入口和业务接入模板。
全量、日更与指定日期修订共用同一个`MinuteMetric`实例所代表的业务逻辑及原执行器，
不再要求为日更复制一套公式。这里的“全量”指本次显式授权日期，不自动扫描全部历史。

## 1. 新增标准入口

公开模块接口为：

```python
from trans_to_min.task_entry import InputsNotReady, run_task_cli

# metric与两个钩子由独立业务项目提供。
exit_code = run_task_cli(
    metric,
    check_ready=check_ready,
    validate_output=validate_output,
    argv=argv,
)
```

主脚本应使用`raise SystemExit(main())`传递退出码。入口模板位于
[`scripts/run_task_template.py`](../scripts/run_task_template.py)，其中的成交量类只是
参考示例。未接入真实上游检查及独立校验时，模板主动拒绝执行，不能删掉门禁冒充适配。

| 模式 | 用途 | 已发布日期的处理 |
|---|---|---|
| `full` | 首次历史范围或显式历史批次 | 来源及算法契约一致时续跑，冲突则拒绝跳过 |
| `daily` | 明确的新日期、漏日或同范围失败重试 | 同样按契约续跑，不自动取昨日或扩大历史范围 |
| `repair` | 经确认的指定日期修订 | 仅重算并覆盖请求日期，保留同月其他日期 |

三个模式均要求显式的`--input-root`、`--output-root`、`--result-json`，日期通过
`--date YYYY-MM-DD`或`--dates-file`二选一。日期文件为UTF-8 JSON字符串数组，
例如`["2025-01-02","2025-01-03"]`；重复日期或非规范ISO日期会被拒绝。
`daily`可显式提交空数组，执行时返回`no_work`且不读源；`full/repair`不允许空数组。

默认不执行：省略`--execute`时只写`planned`计划报告，不读取逐笔源或生成分钟数据。
报告路径必须全新，位于输入和输出目录之外；预演成功不代表上游就绪或校验通过。

## 2. 从全量转为日更的标准步骤

1. 在独立业务目录维护指标公式、README、`generation_spec.json`、参考公式和测试；
   建立唯一入口，并接入上游就绪检查和独立校验。
2. 由可信交易日历与上游发布记录明确本次历史范围；应有但未就绪的日期单独记账，
   不因文件缺失就把日期静默排除。先预演，再按授权执行`full`。
3. 核对历史截止日、逐指标发布范围和所需校验等级；验证一次全量与分批增量结果
   一致，覆盖跨月、月内补日、失败重试和指定日期修订。
4. 保持同一指标类、入口、输出位置和业务口径，仅改为`daily`及明确的新增日期。
   每日按“就绪检查→生成→发布完成→校验→结果对账”顺序运行。
5. 将迟到的新日期显式补入下一次日更；已有日期的输入或公式变更先审查影响，再按
   授权执行`repair`。重试保留原范围并使用新的报告路径，不自动改为覆盖历史。

完整检查清单和预演命令见[历史全量转每日增量标准流程](历史全量转每日增量标准流程.md)。

## 3. 就绪、校验与失败恢复

两个钩子均接收`(metric, config, dates)`，日期以副本传入，不能据此更改入口的请求范围。

- `check_ready`必须检查上游已发布及质检成功的证据；成功返回`None`，未就绪抛出
  `InputsNotReady`。返回`False`不代表成功，文件存在也不代表输入已经发布。
- `validate_output`必须返回可写为JSON的字典，包括`status="passed"`、精确覆盖
  本次日期的`dates`及非空校验等级`level`。独立参考逻辑由业务提供，框架只检查
  声明结构、日期覆盖及校验前后身份，不能替业务证明公式正确或校验等级充分。
- 已通过契约而跳过生成的日期仍属于本次校验范围。因此生成成功但校验失败后，
  重试可以跳过重复计算，再校验同一批已发布数据。
- 校验期间来源或月份文件身份改变会使结论失效；业务校验器自身仍须固定读取版本。

执行入口提供`output_root/metric/.task.lock`同指标互斥锁。它只协调遵守该入口的
调用，不保护绕过入口的旧脚本，也不提供跨指标事务；残留锁不会自动被删除或抢占。

## 4. 结果协议与未来统一调度

独立结果JSON是唯一机器接口，含协议版本、`invocation_id`、指标、模式、请求日期、
生成结果、校验结果、状态、错误和退出码。stdout/stderr可能混有子进程日志，不能
把整串stdout当作JSON，也不能仅凭日志或退出码0宣称已完成生产。

| 退出码 | 含义 |
|---:|---|
| 0 | `planned`、`no_work`或`complete`，必须继续核对JSON状态 |
| 1 | 生成、来源或校验等失败 |
| 2 | 参数、日期或报告路径错误；此时可能没有有效报告 |
| 3 | 上游`not_ready`，由外部依据状态有界重试 |
| 4 | `locked`，先核对同指标任务及残留锁 |

非空正式任务必须同时满足：本次身份及日期匹配、顶层`complete`、生成完成、全部
请求日期通过所需等级校验，且实际退出码与报告退出码均为0。空任务不证明不存在漏日。

后续“一键更新全部分钟数据”仍需轻量总调度器和人工维护的显式任务注册表。注册项
须明确解释器、工作目录、入口、指标、路径、日期来源、上游依赖、报告、资源预算
及最低校验等级。按参数数组启动独立子进程，不递归查找并执行所有Python脚本。
不同业务可使用相同模块名，应隔离导入，避免全局混装。

总调度默认串行；并行时统一约束CPU、内存、Arrow线程与I/O，不能让多个任务各按
可用内存70%独立扩张。完整协议见[统一日更调度接入约定](统一日更调度接入约定.md)。

## 5. 保持不变与明确未实现的部分

- 不改变指标公式、固定242分钟轴、股票集合、NULL语义或四列月Parquet输出。
- 延续1.1.0的三表消费契约：报价口径3、物理格式1；raw框架与分钟框架独立版本化。
- 不自动改造既有信息熵、时间重心、maxdiv等正式业务入口，不重建历史结果。
- 不内置交易日历、上游质检、独立业务公式校验器、定时任务、总调度器、跨任务资源
  仲裁或持久化校验断点；本次提供的是接入接口与约定。
- 标准入口在全量模式也等全部请求日期生成和发布后再校验。只有首次全量可以另接
  外部交错校验，日更不交错。执行器内部“上月发布与下月计算重叠”不等于交错校验。
  外部实现须遵守[交错并行校验要求](逐笔转分钟交错并行校验提示词.md)。
- 框架测试和安装升级不等于正式业务接入、全市场验收或历史数据已经重建。

## 6. 从1.1.0升级的注意事项

框架版本及核心源码参与逐日期来源契约。1.2.0再次请求1.1.0已生成日期时，会因版本
及源码身份不同而拒绝resume跳过；仅追加新日期并不要求重算旧日期。
这是保护门禁，不应绕过。盘点影响范围后决定保持旧环境、受控重建或其他明确方案，
不得自动迁移凭证、把旧日改标为新版本，或为通过门禁擅自扩大重算范围。
仅追加新日时，旧月中未替换日期保留原凭证，并不表示整个历史已采用新版本验收。

更新可编辑安装前，应等待相关生成、发布和校验任务结束；先备份，再切换，最后在
源码目录之外核对实际导入路径、`trans_to_min.__version__`及安装包元数据版本。
生产数据的验收状态与框架源码、安装状态分别记录。

## 7. 安装与自检

Release附件提供核心wheel及`SHA256SUMS.txt`。wheel不包含`docs/`、`scripts/`或
`tests/`；业务模板和文档从仓库对应`v1.2.0`源码获取，业务公式继续由独立项目维护。
环境要求见[README](../README.md)，安装示例：

```bash
python -m pip install trans_to_min-1.2.0-py3-none-any.whl
python -c "import trans_to_min, importlib.metadata as m; print(trans_to_min.__version__, m.version('trans-to-min'), trans_to_min.__file__)"
```

已准备好依赖的离线环境可加`--no-index --no-deps`。源码验收应执行完整pytest，
不能用`unittest discover`替代，因为会漏掉pytest函数测试。测试使用合成临时数据，
覆盖全量/增量一致、跨月、补洞、修订、锁、报告、门禁及失败恢复；不运行生产入口。

本次发布不生成生产数据，不修改既有业务公式或历史分钟结果。
