# 历史全量转每日增量标准流程

本文约定同一业务任务从首次历史构建切换至每日增量的操作流程，配套框架1.2.0的
`trans_to_min.task_entry.run_task_cli`与`scripts/run_task_template.py`。统一总调度器是
后续接入目标，本次不实现；模板不代表现有正式业务入口已完成改造，更不代表生产
历史数据已经重建。接入前须核对实际导入版本、模板、自检与本业务的验收结果。

## 1. 核心原则与职责

一套业务公式、一套任务入口，全量与增量只改变显式日期集合、恢复/覆盖策略和资源
安排，不复制两套公式。框架负责适配、计算、按月发布及来源门禁；业务负责公式、
输入就绪判断与独立校验；调度方负责可信交易日、上游完成清单、漏日对账及总资源。

正式输出仍为每指标独立四列分钟长表和月Parquet，不因日更改为每日文件或宽表。
分钟轴、股票范围、事件/订单单位、NULL规则及公式均沿业务规格，不随运行模式变化。
日频因子如由分钟结果继续构建，其因子宽表和收盘后可见性约定由下游业务维护。

开始前读取README、CHANGELOG、AGENTS、当前适配器/执行器、相关测试、
[交错校验要求](逐笔转分钟交错并行校验提示词.md)及
[三表到分钟统一契约](逐笔三表到分钟统一契约.md)。涉及L2消费变化，还须读最新
三表任务书及分钟交接规范，不能把旧试验报价版本2当作最终生产口径。

## 2. 先完成业务接入

业务项目提供可追溯实体模块中的`MinuteMetric`实例，再调用：

```python
from trans_to_min.task_entry import run_task_cli

def main(argv=None):
    return run_task_cli(
        metric,
        check_ready=check_ready,
        validate_output=validate_output,
        argv=argv,
    )
```

示例中的`metric`及两个钩子必须由业务实现。仓库模板仅复用已有
`MinuteTradeVolume`用法，不定义正式业务公式；默认就绪与校验钩子未接入，执行时
会拒绝继续，不能将删除门禁当作完成适配。业务必须同步逐指标README、
`generation_spec.json`、独立参考公式、测试及版本身份，验收后才可正式运行。

两个钩子签名均为`(metric, config, dates)`，日期为本次显式请求范围：

- `check_ready`核对所有请求日期的上游成功清单、输入表集合、版本、质检和身份；
  成功时正常返回`None`，未就绪时抛出`InputsNotReady`；返回`False`等值会报错，
  不能把否定结论误判为成功。目录或文件存在不等于上游已经成功提交。
- `validate_output`读取本次全部请求日期的当前已发布结果，包括resume跳过生成的
  日期，返回含`status="passed"`、精确ISO日期列表`dates`、非空`level`的字典。
  `level`如实说明结构检查、样本参考或全范围独立公式等级，不能以低等级冒充高等级。
  公式参考由业务自行提供，不得直接调用待验证生产公式得到“参考值”。

独立校验还需核对发布凭证和固定文件版本；同一月文件可能被原子替换，不应多次按
路径打开后误以为仍是同一快照。校验状态不得回写生产Parquet或补造生成manifest。

## 3. 统一命令与安全默认值

入口强制显式传入`--mode full|daily|repair`、`--input-root`、`--output-root`、
`--result-json`，并从以下两种日期方式中选择一种：

- `--date YYYY-MM-DD`：单一显式日期。
- `--dates-file 文件`：UTF-8 JSON ISO日期数组，例如`["2025-01-02","2025-01-03"]`。

不隐式取昨日，不从输入目录发现历史日期，也不把缺日期参数解释为全量。
日期应由可信交易日与上游完成记录求交后明确提交；尚未就绪的应有日期另记等待，
不得在求交时静默丢失。日期规范化排序且不得重复，交易日遗漏不能靠目录扫描发现。
`daily`允许显式空数组`[]`，返回`no_work`且不读取源数据；`full`和`repair`拒绝空数组。
空任务只表示本次没有请求，不能证明无漏日，调度方仍须对账。

未加`--execute`仅生成`planned`计划报告，不生成分钟结果，也不证明输入已就绪或
业务校验通过。`full`与`daily`默认使用来源门禁保护的resume；`repair`只重算并覆盖
显式请求日期，保留同月其他日期。恢复与覆盖互斥，不能为通过门禁静默改成覆盖。

可设置`--date-workers`、`--arrow-threads-per-worker`及`--auto-memory-fraction`。
首次全量可以采用较大但有界的日期并发；每日小批次通常使用较小并发。资源选择需
实测单worker峰值、Arrow线程和I/O，不因服务器内存大或有GPU就无约束加进程。

每次调用必须指定全新的结果JSON路径，且不能位于输入或输出目录子树，也不能
覆盖已有文件；日志与报告放独立工作区。写报告不等于授权写生产数据。执行入口锁
`output_root/metric/.task.lock`防止同一指标入口互相覆盖，残留锁不自动抢占；旧脚本
绕过入口时不受此锁保护，运行前还须排除旧进程对同一路径的并发写入。

以下仅是隔离工作区的dryrun示例，路径不是生产目录，日期文件须预先显式建立。
模板钩子未适配时不得加`--execute`用于正式任务：

```powershell
python scripts/run_task_template.py --mode full --dates-file D:/sandbox/trans_to_min_case/full_dates.json --input-root D:/sandbox/trans_to_min_case/input --output-root D:/sandbox/trans_to_min_case/output --result-json D:/sandbox/trans_to_min_case/reports/full_plan_001.json --date-workers 1 --arrow-threads-per-worker 1 --auto-memory-fraction 0.20
python scripts/run_task_template.py --mode daily --date 2025-01-06 --input-root D:/sandbox/trans_to_min_case/input --output-root D:/sandbox/trans_to_min_case/output --result-json D:/sandbox/trans_to_min_case/reports/daily_plan_001.json --date-workers 1
```

## 4. 首次历史全量

1. 冻结指标、算法、输入及校验器身份、可信交易日范围和本次授权目标集合；保存
   独立范围清单，明确缺源、旧源和尚待重建日期，不按现有分钟文件反推目标。
2. 在隔离目录测试单日、跨月、月内补日、失败恢复、缺源、NULL及订单边界；同一
   输入与代码下比较一次全量与分批增量的日期、键、值、NULL、类型及来源契约。
3. dryrun核对范围、路径和资源，再经本次授权使用同一入口的`full --execute`。
   首次全量不是绕过resume契约的理由；已有旧凭证不匹配时先停下审查。
4. 本入口采用保守顺序：生成全部请求日期→等待正式发布完成→校验全部请求日期。
   月份发布与后续月份计算的执行器内部重叠，不等于生成与校验交错。
5. 大范围首次全量如需外部交错校验，按交错校验要求另行实现并验收动态就绪、固定
   版本、独立校验断点和全局资源协调；不得只修改文档后宣称入口已内置交错能力。
   有待计算日时启动不立即落running manifest，须确认本次`run_id`；异步检查点
   可延迟整月，文件存在不等于匹配检查点已提交，不能借旧manifest冻结本次范围。
6. 对账本次全部授权目标的正式发布与所需校验；只有生成成功且当前版本全部通过
   才完成。保存范围、参数、源码、安装位置、报告、日志与校验等级。

## 5. 切换至每日增量的检查清单

- 历史截止交易日明确；逐指标目标、已发布、已校验、失败、待发布和失效数量对齐。
- 漏日、缺源、旧口径与尚未重建范围已列明，不能用“全量完成”掩盖未验收部分。
- 历史月份与日更将使用同一业务模块、入口、分钟轴、值类型、NULL和来源契约。
- 单次全量与多批增量一致性测试通过；月内插入、跨月、新月、指定日修订均已覆盖。
- 每日候选日期来源、上游成功清单、业务就绪钩子及独立校验器已接入并完成失败测试。
- 明确日更起点、补漏窗口、迟到数据等待/告警期限及修订审批；不简单等同“昨天”。
- 使用全新报告路径、稳定任务身份与输出锁；确认没有旧入口并发写同一指标。
- 实际导入的框架版本、部署代码与测试一致；代码同步不代表历史结果已自动更新。

## 6. 每日例行流程

调度方先根据可信交易日、业务截止时间、上游成功清单与任务账本，计算尚待完成或
上次校验失败的显式日期集合。无交易日可以提交空数组，但必须记录空任务原因；
应有交易日却返回空集合、某输入缺日或上游失败应告警，不能伪装成正常休市。

每日仍走“就绪检查→resume生成→发布完成→校验本次全部请求日期→结果对账”。
每日不交错生成和校验，也不扫描或重校全部历史。若上次生成成功而校验失败，重试
原请求日期：生成可以resume跳过已发布日，校验仍覆盖这些日期，避免误报完成。
本入口不提供独立的持久化校验断点服务，业务需要复用结论时自行保存版本化证据。

可信上游未就绪返回`not_ready`，等待后以新报告路径重试；公式、类型、来源或校验
错误返回`failed`，先诊断再决定是否重试。锁冲突返回`locked`，先确认锁所属进程与
任务记录，不自动删除锁、不终止用户进程。每次重试保留原范围，不无意扩大为历史。

## 7. 迟到、修订与升级

迟到但此前未成功发布的日期，在就绪后加入下一次显式`daily`集合；重复请求只有
来源及代码身份一致才可resume。已发布日期的输入修订或业务公式变化不属于普通
补日，应列出受影响指标×日期，经授权使用`repair`，校验完成后更新任务账本。

框架来源契约包含框架版本、核心源码与业务源码身份。升级至1.2.0后，再次请求
1.1.0已生成日期会因契约不同而拒绝resume跳过；仅追加新日期并不要求重算旧日期。
即使版本号未变，调整被摘要纳入的源码也会使原契约失配。这是保护门禁，不是可忽略的
噪声。先盘点影响并决定保持原环境、受控重建或另立兼容方案，不自动迁移凭证、
补造契约、重建历史或把旧结果标记为已适配。源码、安装和生产数据是独立状态。

同步前检查正在运行的生成和校验进程。活动任务可能持续读取框架源码计算契约，
不得在运行期间直接覆盖其可编辑安装目录或替换公共环境。先同步独立版本目录并
完成自检，等相关任务自然结束或获准维护窗口后，再备份、切换并核对安装元数据。
待切换目录与本地一致不等于服务器活动安装已经升级，交付时必须分别报告。

若只授权新日期，不因升级自行重算旧日期；若新日期与旧月结果合并，未替换日期
仍保留原凭证，不代表整月已采用新代码。历史验收范围必须单独说明。

## 8. 完成判定与交接

结果JSON文件是唯一机器接口；stdout/stderr可能包含日期子进程业务日志，不能将
整个stdout当作JSON解析。退出码0可能是`planned`、`no_work`或`complete`，不得只看进程结束或日志文字。
应核对本次结果JSON的协议版本、调用身份、模式、指标、精确请求集合、退出码、
生成状态和校验等级/覆盖。详细协议见[统一日更调度接入约定](统一日更调度接入约定.md)。

任何未发布、失败或失效目标都应汇总报告。正式运行前服务器写入、取数、数据库或
网络操作仍须遵守AGENTS的说明与授权要求；本文示例不是执行生产或扩大范围的授权。
