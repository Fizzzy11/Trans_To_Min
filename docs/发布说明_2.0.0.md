# Trans_To_Min 2.0.0 发布说明

2.0.0 把并行调度、日内按股票分块、资源分配和校验等级都收进了框架。新任务只写指标公式
和独立参考，用一个运行配置启动；任务里不再写调度、并行、暂存、清理和管控代码，也不允许写。

1.4.0 的接口和执行方式全部保留，旧的七项任务（四项基础、entropy、maxdiv、time_center）
不迁移也能照常运行；分钟轴、四列 Schema、月文件层级和发布逻辑都不变。

## 1. 新任务怎么写

### 1.1 任务目录

任务目录只允许包含：

- 指标包（含 `__init__.py`）；
- `README.md`、`CHANGELOG.md`、`AGENTS.md`、`generation_spec.json`、`pyproject.toml`；
- `docs/`、`metric_docs/`、`tests/`、`reports/`、`run/`（存放运行配置）。

不允许出现 `operations/`、`scripts/`、私有框架副本、自建控制器。`scripts/audit_task.py` 会检查这些。

### 1.2 指标声明与分块计算

指标仍用 `MinuteMetric` 子类声明名称、输入表、字段、`value_type` 和 `empty_value`。
`prepare_events` 不会被调用，实现为 `raise NotImplementedError` 即可。

计算写在 `BlockMetricGroup` 的子类里，只实现一个方法：

```python
import numpy as np
from trans_to_min import kernels
from trans_to_min.blocks import BlockMetricGroup, CellValues


class TradeGroup(BlockMetricGroup):
    def compute_block(self, block, metric_names):
        table = block.tables["chengjiao"]
        valid = table["minute"] >= 0            # 分钟轴内的行
        cells = block.cells("chengjiao", valid)  # 块内"股票×分钟"格键，非降序
        return {
            "x_volume_min": CellValues(*kernels.sum_by(cells, table["volume"][valid])),
            "x_count_min": CellValues(*kernels.count_by(cells)),
        }
```

`block.tables[表名]` 是各声明字段的 numpy 数组，不含 symbol，另有两列：

- `stock`：块内股票序号；
- `minute`：0~241 的分钟序号，分钟轴外为 -1。

行的顺序约定如下：

- 行按股票排序；
- 分钟轴内的行按分钟非降序，同一分钟内保持源文件顺序；
- 轴外的行位置不作保证，按 `minute >= 0` 筛掉即可。

数组都是只读的。

`CellValues(keys, values, nulls=None)` 给出块内各格的结果：

- 没出现的格按 `empty_value` 填充；
- `nulls` 标记应为 NULL 的格。

框架会检查结果：必须恰好覆盖所选指标，格键不能越界或重复，三者都必须是 numpy 数组。

强制约束：

- 定义 `BlockMetricGroup` 子类的模块不得导入 pandas，`compute_block` 也不得引用 pandas。
  违反时，类定义阶段就会报 `TypeError`。pandas 只允许用在独立参考等其他模块。
- 组内各指标的盘前、盘后折入设置必须一致。每张输入表都必须声明 `time_ms`，
  不能声明 `timestamp`。
- 确实不能按股票拆分的指标（例如截面排名），可以继续用普通 `MinuteMetricGroup`，
  但必须设置 `whole_day_reason = "理由"`。理由会写进运行报告和 bench 报告。

### 1.3 分段运算（`trans_to_min.kernels`）

| 函数 | 用途 |
|---|---|
| `runs(keys)` | 非降序键的唯一键与段起点 |
| `sum_by(keys, values)` | 分段求和。整数在 uint64 域求和，溢出时报错；浮点固定用 `np.add.reduceat`，不允许含 NaN |
| `count_by(keys)` | 分段行数 |
| `min_by`、`max_by`、`first_by`、`last_by` | 分段最小、最大、首行、末行 |
| `distinct_count_by(keys, ids)` | 段内不同身份数，例如分钟订单数；用打包排序实现，不用哈希 |
| `pack(*columns)` | 把多列非负整数按位拼成一个 uint64 键 |
| `group(keys)` | 无序键稳定排序分组；提供 `Groups.sum`、`count`、`take`，`broadcast` 可把组结果映射回原行，例如"先按订单号算全日金额，再回到每笔事件" |
| `cell_keys`、`dense` | 格键编码、稀疏结果展开 |

缺值行由调用方先筛掉。不要把缺值当作 0 送进求和。

### 1.4 任务工厂与独立参考

任务提供一个工厂函数，返回 `TaskGroup` 列表：

```python
from trans_to_min.plan import TaskGroup
from trans_to_min.reference_check import DayReference

def build_task_groups():
    return [TaskGroup(
        TradeGroup("x_group", [XVolume(), XCount()]),
        {"x_volume_min": "vol_min", "x_count_min": "count_min"},  # 指标→任务输出目录下的子目录
        DayReference(day_reference, level="抽样日全股票独立复算"),
    )]
```

每个组都必须有独立参考，写法须与生产不同。接口同 1.3.0：模块级函数
`(trade_date, sources)`，只用 `sources[表].open()` 读数，返回全部股票×242 的数组。

## 2. 怎么运行

```toml
# run/full_2024_2026.toml
[run]
mode = "full"                 # full：已发布日期跳过 | daily：日更 | repair：重算覆盖
start = "2024-01-01"
end = "2026-09-30"
output_root = "/sd1-data/trans_to_min"
state_root = "/data/zhangyuan/<项目>/runs/full_2024_2026"   # 不得位于output_root内
validation = "light"
bench_report = "/data/zhangyuan/<项目>/bench"              # full模式必填
# memory_fraction = 0.95     # 只能调低
# months_per_job = 1

[[task]]
name = "x_min"
path = "/app/workspace/zhangyuan/逐笔转分钟数据/x_min"
factory = "x_metrics.groups:build_task_groups"
```

```bash
python -m trans_to_min run run/full_2024_2026.toml            # 预演：只打印计划
python -m trans_to_min run run/full_2024_2026.toml --execute  # 执行
```

- **作业单位**：一个作业是"任务×月"，子进程同样由框架入口启动（`python -m trans_to_min worker`）。
- **共用读盘**：配置里列出的多个任务，凡读同一张逐笔表的，自动对齐到同一月份，共用暂存，
  每个源文件只读一次盘。
- **续跑**：中断后以同一配置重跑即可，已发布的日期跳过。在 `state_root` 下创建 `STOP` 文件，
  调度器就不再派发新作业，等已运行的作业结束后退出。
- **结束清理**：自动清除暂存、`.group_staging`、锁；没有失败时，参考检查点也一并清除。
  只写一份 `run_report.json`，包括日期数、耗时、单日期进程峰值、每行字节数、吞吐和失败作业；
  另有 `state.json` 记录进度，每个作业一份 `result.json`。

## 3. 资源分配

- 内存总预算为总内存 × `memory_fraction`，默认 0.95，也是上限；源文件暂存预算计入其中。
- 每个日期进程按"当日输入行数 × 每行字节数 × 1.15"预留内存。每行字节数初值取 200，
  每个作业结束后按实测峰值校准，可以向上也可以向下调整。
- 派发前同时检查剩余预算和当前 `MemAvailable`（扣除 8G 余量）。任一不足时只暂停派发，
  不终止已运行的作业。
- 每个日期进程的分块线程数 = CPU 核数 ÷ 同时运行的日期进程数，限制在 1~16。块大小默认
  25 万行（`RunConfig.block_row_budget`）。

## 4. 校验等级

- `light`（默认）：所有日期做结构检查，即每个日期都已发布、行数恰为股票数×242。另外最多选
  3 个代表日（最大输入日、首日、末日），由独立参考对全部股票复算。代表日之外的日期不产生
  参考计算的开销。
- `full`：所有日期都做独立复算，必须在配置里显式写明；`audit_task.py` 会提示需要说明理由。

## 5. 效率门禁（bench）

```bash
python -m trans_to_min bench run/full_2024_2026.toml --task x_min --date 2024-xx-xx \
    --work-root /data/zhangyuan/<项目>/bench_tmp --report-dir /data/zhangyuan/<项目>/bench
```

- 在隔离目录跑一个真实大日（应选近年的大日），报告输入行数、耗时、峰值内存和每行字节数，
  跑完删除隔离目录。
- 门槛：每行字节数（日期进程峰值 ÷ 当日该任务全部输入表行数）不超过 **250**。实测参照：
  分块示例组约 124；pandas 整天写法约 196；1.4.0 四项基础任务约 110~192。
- full 模式启动前检查每个任务的 bench 报告：必须达标，且晚于任务目录中最新修改的 `.py`，
  代码改过就要重跑 bench。只比较文件时间和数值，不做哈希。

## 6. 验收检查

```bash
python scripts/audit_task.py --task-dir 任务目录 --output-dir 任务输出目录 \
    --plan 运行配置.toml --scratch /data/zhangyuan --scratch /dev/shm
```

由用户或验收方运行，只读。检查项：

- 目录结构；
- 有无框架副本；
- 有无修改 `sys.path` 或给框架打补丁；
- 有无自建进程调度；
- 定义分块组的模块是否导入了 pandas；
- 有无疑似自建凭证或审批的管控；
- manifest 里的框架版本和导入路径；
- 资源比例与校验等级；
- 有无遗留的中间数据。

有任何问题即不验收。manifest 自 2.0.0 起记录 `framework_module`，即框架的导入路径。

## 7. 其他改动（旧任务同样受益，结果不变）

- 适配器读数：symbol 直接按字典解码为分类，不再先物化上亿个字符串；bytes 检查只看分类值；
  列重排不再整表复制。2022-02-24 成交表（1.085 亿行，5 列）读数从约 26 秒降到约 10 秒，
  5 列结果和类型与原实现逐位一致。
- 分钟编码改为"向上取整到分钟再查表"（`minute.minute_codes`）。与原逐掩码实现相比，
  在每个整分钟前后各 2 秒的全部毫秒、加上 200 万个随机时刻上，4 种盘前、盘后组合都完全一致。

## 8. 实测（2022-02-24 成交表，1.085 亿行，4 个示例指标）

| 写法 | 计算耗时 | 峰值内存 |
|---|---|---|
| pandas 整天（1.4.0 普通组） | 270.4 秒 | 19.8G |
| 分块，1 线程 | 26.4 秒 | 12.5G |
| 分块，每块 25 万行，16 线程 | 5.3 秒 | — |

- 各线程数、各块大小下的结果与 1 线程逐位一致。分块与 pandas 整天相比：键和整数列逐位一致；
  浮点金额最大相对差 5.7e-16，原因是 pandas 的求和带补偿，kernels 不带。
- 单日期进程超过 16 线程不再变快，剩下的约 2.7 秒是单线程的股票编码和结果合并。
  整机算力靠"多个日期 × 每日期线程"用满，这由调度器分配。

## 9. 不在本版本内

- 跨股票的指标（截面排名等）没有第二阶段，只能走整天计算，并须声明 `whole_day_reason`。
- 不做账号隔离，也不做框架启动自检；`audit_task.py` 是验收时的事后检查。
- 旧七项任务不迁移。

## 10. 运行边界与注意事项

- 统一调度器依赖Linux的`/proc`及进程组；Windows可使用旧接口、构包与跨平台测试，不能据此
  宣称完整调度已在Windows运行。没有GPU计算或多机分布式调度。
- 分块针对计算：适配器仍先读入完整交易日的所需列，再按完整股票切块；不是逐块读盘。
  单只股票超过行预算时独占一块，不拆订单，因此25万行不是每块内存的硬上限。
- 多任务工厂应使用互不重名的顶层Python包。当前主调度进程不隔离同名模块的导入缓存，
  多个旧任务都叫`minute_metrics`时，不可直接放入同一个新运行配置；旧入口仍可分别运行。
- 同一输出范围只能由一个调度实例管理；本版本没有跨实例总锁或账号隔离。`STOP`停止新增
  派发并等待运行中作业结束；发送终止信号则会终止已派发作业，两者不同。
- 默认预演不生成分钟数据，但会创建状态目录和日志、加载任务并读取输入元数据；不是完全
  无文件写入。日期由配置起止范围内的源文件集合确定，不内置交易日历、上游日更触发或质检。
- `light`的结构检查和最多3个代表日复算针对本次待生成日期；全部已发布的日期直接跳过，
  不因再次执行运行配置自动复验全部历史。改公式后需要维护者显式选择`repair`重算。
- 分块浮点求和固定为非补偿归约，不能承诺与旧Pandas补偿求和逐位一致；迁移业务时明确
  容差及缺值规则。NULL、无事件和零仍须由指标显式区分。
- 本次同步发布不迁移业务任务、不重算生产数据，也不重新执行上述真实大日性能实验。
