# 逐笔转分钟业务开发必读：边界、性能与兼容性

适用于所有基于 Trans_To_Min 的分钟数据任务。**设计任何新任务或改造旧任务前必须完整读完本文**，
再读 README、CHANGELOG 与相关契约文档。本文记录已实测的数据事实、框架行为、性能陷阱和
存量/日增量的运行约束；它是开发提示，不修改框架行为，也不替代各任务自己的口径定义与验收。

来源：2026-11-11 四类基础分钟（wt/cd/cj/acj_basic_min）三日试跑核查与提速。所有数字为
hytp_server 实测，换数据规模或机器后须重新测量，不能当作承诺值。

## 一、正式三表的数据事实（设计前必须知道）

1. **排序**：`/sd1-data/level2/{dataset}/...` 每日文件按 `symbol` 字典序、同一股票内按 `time`
   非降排列（2020、2022、2023、2026 年三表抽查均成立，跨 row group 亦成立）。因此同一
   “股票×分钟”的正常分钟记录在物理行上**连续**，同毫秒按物理行序即为稳定顺序。
   业务可利用这一点做分段归约，但**必须先检查有序性，不成立时稳定排序回退**，不得假定。
2. **物理类型**（format_version=1，price_policy_version=3）：symbol string、date date32、
   time uint32（午夜起毫秒）、order_num/buy_order_num/sell_order_num uint32 非空、
   volume uint32 非空、side uint8（48/49/50）、price int64（委托/撤单可空）、money int64（仅成交），
   price_scale=money_scale=10000（以 footer 实际值为准，不硬编码）。
3. **规模**：2026 年单日委托 2.0–2.3 亿行、成交 1.1–1.2 亿行、撤单约 0.5 亿行；2020 年约为其
   1/3。2020-01 至今约 1660 个交易日，三表压缩合计约 3.3TB。
4. **存储介质**：`/sd1-data` 为单块 16TB 机械盘，实测顺序读约 218MB/s，4–8 路并发总吞吐
   不升反降（约 195–215MB/s）。`/data` 为另一块机械盘。存量任务的下限通常由**读盘总字节**
   决定，而不是 CPU 或进程数。
5. **真实极端值**：委托/撤单价格包含交易所接受的远端限价申报（如创业板卖单 9999、999999 元），
   不是哨兵值；价格类指标（OHLC）会直接反映，下游需自行处理。

## 二、适配器（L2InputAdapter）行为与边界

1. `volume` 与订单号字段在适配器内转 uint64。**1.2.2 及以前**直接 `astype(uint64)`：负数静默
   绕回为极大值、小数静默截断，空值抛 `IntCastingNaNError`。**1.2.3 起**有符号/浮点/可空来源
   在转换前检查空值、负数、小数、非有限值及超出uint64范围并报 `ValueError`；
   非空无符号物理列零开销直通，可空物理列含NULL仍拒绝。
   业务层在适配器之后再检查“负数/小数”仍然无效（已转成 uint64）。按 1.2.2 运行的业务可保留
   单事件数量`>= 2**63`异常兜底（真实数量不可能达到），但它不能代替分组求和的独立溢出检测。
   直接构造 DataFrame 的单元测试绕过了适配器，
   **不能证明生产链路能拦截非法值**；必须有经过真实 Parquet + 适配器的测试。
2. 订单号可空豁免分支在适配器路径上不可达（空值先在适配器失败）。设计“允许零/空引用”
   的业务分支前，先确认真实读数链路能把这类值送达业务层。
3. **声明字段即内存成本**：
   - 声明逻辑字段 `money` 而物理表无 money（委托/撤单）时，适配器会对**全日（含盘后）**
     派生 price×volume 一整列 float64；
   - 声明 `trade_date` 会生成 datetime64[ns] 全列（8 字节/行）；
   - symbol 为 category，time_ms 为 uint32，volume 统一为 uint64。
   只声明公式与质检真正需要的字段；适配器已派生的列不要在业务层再算一遍再做全量比对。
4. 读入成本参考：2.03 亿行委托（6 个逻辑字段）适配器约 37 秒、常驻约 16G、峰值约 25G。

## 三、框架接口的性能陷阱

1. **股票全集（1.2.4 起由框架自动处理）**：执行器单日作用域内，`symbol_union` 对同一张输入表
   只真正计算一次，组内各指标（默认或自定义组、`compute_day` 或 `finalize_aggregated_day`）自动复用。
   - 业务**直接把执行器给的完整 inputs 传下去**，不要自己算全集、不要构造只含 symbol 的小表、
     不要传 `symbols=`（为兼容保留，传入时必须等于 `symbol_union(inputs)`，否则报错）。
   - **不要原地改写输入表的 symbol**：执行器读入后、交给业务前登记输入并把 symbol 编码设为只读，
     直接或经切片/视图单格改写都会报 `assignment destination is read-only`；需要变换 symbol 时先
     `copy()` 再改。只有执行器登记的输入才缓存；业务自建、切片或复制的表每次重新计算。
   - 自己写执行器或在执行器外调用时，用 `symbol_universe_scope(inputs)` 在刚读入、尚未交给业务前登记；
     不登记则不缓存，结果仍正确。
   - 不要把筛选后的新表当输入传给 `symbol_union`/`finalize_aggregated_day`：全集口径是完整、
     未筛选输入中实际出现的非空 symbol（含仅盘后出现的股票）。
   - 实测（2026-09-28 委托 2.29 亿行）：原方法每次约 1.9 秒，13 个指标约 24 秒；1.2.4 每天合计约 1.6 秒（含登记副本约 0.24 秒）。
   - 1.2.3 及以前每个指标各扫一遍；当时的变通是传小表或 `symbols=`，升级到 1.2.4 后应删掉。
2. `MinuteMetricGroupRunner` 按**月**推进：月内日期进程数上限为当月交易日数，月与月之间有
   屏障；同一主题同时只能有一个 runner（manifest 并发写会冲突）。跨月并行需要业务层
   调度器（按“任务×月”派发），不能对同一主题并发启动多个 runner。
   `publish_while_computing=True` 可让上月发布与下月计算重叠，属于配置项。
3. `recommend_date_workers` 按“未压缩输入×倍数”估算单进程内存：框架默认
   `auto_worker_memory_multiplier=16`（`config.py`）；四类基础分钟的业务入口
   `runtime.py --auto-worker-memory-multiplier` 默认 32，二者不要混用。wt 优化后实测约为输入
   未压缩量的 10–12 倍。存量调度应以**实测峰值/输入大小**反推倍数并持续校准。
4. 只在新业务确实需要时才用 `aggregate_minutes` 的逐分钟 Python 回调，它不适合亿级行。

## 四、亿级逐笔的计算实现要点（实测）

| 做法 | 1–2 亿行实测 | 备注 |
|---|---|---|
| Pandas `groupby` 哈希分组（多次） | 委托 13 指标约 41 秒 | 每个 groupby 都重新分解键 |
| 有序分段 `np.add.reduceat`/`fmax.reduceat` | 同等指标约 5–10 秒 | 需源有序或先稳定排序 |
| `pd.unique` 哈希去重 1.13 亿 uint64 | 11.3 秒 | 键接近有序时也不变快 |
| `np.sort(kind='stable')` 后数相邻变化 | 1.5 + 1.5 秒 | 接近有序数据上接近线性 |
| `Series.iloc[位置数组]` 取子集 | 1.13 亿行 5 列约 6.8 秒 | 改用 `to_numpy()[mask]` |
| 结构化数组 `np.unique` | 成交参考校验每日约 330 秒 | 改 lexsort 后数变化 |

1. 键编码：`股票排序位置×242+分钟码` 得到稠密整数键，键空间约 130 万；按源有序直接得到
   分段起点，不必哈希。
2. 计数去重：把“分段号<<32 | 32 位订单号”打包为单个 uint64 再稳定排序；有序订单对先给
   (分段,买号) 编紧凑序号，再与卖号打包，避免超过 64 位。订单号超出 32 位时回退通用路径。
3. **数量求和**：uint64 归约溢出会静默回绕，必须检测（例如并行做 float64 近似和，≥2^63 的
   分段改用 Python 整数核验）。不能用 float64 累加数量冒充精确（2^53 以上失真）。
4. **金额求和精度**：Pandas groupby sum 带 Kahan 补偿；普通 float64 顺序累加（bincount、
   reduceat）在单分钟数万行时相对误差可能超过 1e-12 的验收容差。
   - **不要依赖 `np.longdouble`**：它的实际精度取决于平台、编译器和NumPy构建。常见
     Linux x86_64构建采用80位扩展精度，常见Windows/MSVC构建与float64相同（尾数52位）；
     其他平台可能采用不同表示，须检查当前环境，不能将平台示例当作穷尽或唯一条件。
   - 推荐按分段号做 Pandas 分组求和（`Series.groupby(分段号).sum()`，Kahan 补偿，纯 float64
     运算）。四类基础分钟在已验证环境实测与原groupby实现逐位相同，耗时与longdouble相当；
     这不保证所有平台、编译器及依赖版本间逐位一致。
   - 方向分支（买/卖、已知价）**只把选中的行送入求和，不要用 0 占位**：Kahan 在加 0 时也会把
     补偿项并入和，末位就和“只加选中行”不同（实测约 0.01% 的格子差 1–2 ulp）。
   - 需要精确和时，在物理整数域（int64/Python 整数）求和后再除 scale。
5. 缺价/NULL：金额分支须单独保留“有事件数”和“已知金额数”，K=0 输出 NULL，无事件不输出
   （由框架填 empty_value）；`fmax/fmin.reduceat` 忽略 NaN，`maximum.reduceat` 会传播 NaN。
   取首末已知价时，**全部缺价（已知价行数为 0）** 要单独处理：空位置数组不能再拼接
   `np.r_[True, ...]` 之类长度为 1 的掩码去索引，否则 IndexError。必须有“全日仅一条缺价事件”的测试。
6. 不要整表 `frame.loc[mask, columns]` 复制；按列取 numpy 数组并只复制需要的列。
7. 独立参考校验应采用与生产不同的算法（例如生产哈希/打包排序，参考 lexsort），并**按日期
   多进程（spawn）并行**；单进程逐日串行的校验会成为存量瓶颈。

## 五、存量全量与日增量的运行约束

1. **先定版再跑存量**：1.4.0 起框架不保存来源凭证（已发布日期默认可信），业务包或框架代码改动不再使
   已发布结果不能 resume，框架也不会提醒。存量开跑后若改了公式，须自行对受影响日期用
   overwrite_dates 重建，否则同一数据内会新旧口径混存。
2. **源文件只读一次（1.3.0 起由框架强制）**：
   - 执行器经 `trans_to_min.source_stage` 把每个逐笔日文件按文件身份在内存盘只暂存一份；
     生成、独立参考、读取同一张表的其他任务都从这份字节解码，机械盘只被顺序读一次；
   - **业务代码不得自行按路径打开逐笔源文件**。生产公式只用执行器给的 `inputs`；独立参考写成
     模块级函数 `day_reference(trade_date, sources)`，只用 `sources[dataset].open()` 读取，
     以 `DayReference` 交给执行器；校验调用 `reference_check.validate_published`，
     它读已发布月文件与生成期检查点逐值比对，不再重读源文件；
   - 共享按文件身份自动成立，与任务是谁无关：读同一张表就共享，不读同一张表互不影响。
     调度器让读同一张表的任务推进到相同月份并设 `source_stage_retain=True`，结束时
     `source_stage.clear()`；日频调度先 `stage_files` 当天三张表，全部任务结束后 `release`；
   - 暂存占内存盘（计入内存），派发预算须扣除 `source_stage_budget_gb`；
   - 暂存副本与 `.reference_checkpoints` 都是中间数据，批次结束后必须清空，
     输出目录只留分钟数据本身；
   - 输出尽量写到与源不同的磁盘。
3. **共享服务器**：派发前读取实际可用内存（MemAvailable），其他用户进程会占用资源。
   超预算只暂停派发新作业，不终止已在运行的作业。
4. **上游就绪凭证**：
   - 2020–2022、2024、2025：各年 `rebuild_{年}_v3*/final_verification.json`（passed、报价3、格式1）；
   - 2023：`publication_resume_20261009_01/final_verification.json`（passed，242 日、726 文件，
     先发布 205 日 + 续发 37 日）。`rebuild_2023_v3_20261009_01/status.json` 的 failed 只是
     恢复前的原始状态，不是最终结论；找年度证据时要同时查发布恢复目录；
   - 2020-01-02 至 2026-09-30 全部 4908 个正式文件身份：
     `clear_level2_demo_20261013_01/formal_source_map_after_clear.json`；
   - 2026-10-08 起：`/data/zhangyuan/level2_daily_update/daily_formal/state/days/{日期}.json`
     （status=success，含三表 inode/size/mtime/rows/sha256）。
   以上目录均在 `/app/workspace/zhangyuan/test_make_dir/逐笔数据存储优化/reports/` 或上游日更
   数据目录；凭证只核对、不补写，不得按日期猜版本。
5. **日增量**：交易日只取上游成功日期，不扫描目录猜日历；上游 21:00 日更完成后触发；
   上游文件身份变化导致契约不符时只报告并等待授权 repair，不自动覆盖。

## 六、实测参照（2026-09-28至30三日，2026年数据规模）

| 任务 | 原实现生成+校验（单任务串行） | 优化后（四任务并行、每任务3日期进程） | 单进程峰值 |
|---|---|---|---|
| wt_basic_min | 730 秒 | 331 秒 | 50G → 31G |
| cd_basic_min | 267 秒 | 142 秒 | 14G → 8.4G |
| cj_basic_min | 1610 秒 | 211 秒 | 37G → 32G |
| acj_basic_min | 656 秒 | 180 秒 | 38G → 26G |

优化只改业务层实现，口径不变。“一致”分两个层次，验收时要写清是哪一层：
- **逐位相同**：与原实现试跑的已发布结果相比，键、NULL、整数、价格、金额全部逐位相同
  （2026-11-11 改补偿求和后，四任务三日 67,510,588 格非逐位 0；compare_v4）。
- **容差内一致**：与独立参考（整数域精确求和）相比，金额按 1e-8+1e-12×|参考| 判定，
  147,553,692 个值无超差（e2e_01，旧longdouble候选实现的端到端证据，不代表新版
  补偿求和实现已重新执行端到端校验）。容差内一致不等于浮点逐位相同；上述结论仅覆盖
  当时已验证的环境、版本和范围，不作所有平台与依赖版本的逐位保证。

## 七、设计任务时的检查清单

- [ ] 指标公式、输入表、字段、事件时间、股票全集、空值、类型、目录已列清；
- [ ] I/O 组按物理输入表集合划分，每表每日一次正文读取；
- [ ] 只声明必要字段，估算适配器读入内存；
- [ ] 确认源有序性假设并实现回退；
- [ ] 数量精确与溢出检测、金额精度、NULL 语义有对应测试；
- [ ] 有经过真实 Parquet + 适配器的非法值测试；
- [ ] 单日实测耗时与峰值内存，按机械盘吞吐估算存量总时长；
- [ ] 独立参考与生产算法不同，写成 `DayReference`，只经 `sources[dataset].open()` 读源；业务包内没有任何按路径打开逐笔源文件的代码；
- [ ] 存量开跑前源码定版，运行工具在业务包外；
- [ ] 日增量的上游凭证、日期来源、触发与修订处理已设计。
