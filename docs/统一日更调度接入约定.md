# 统一日更调度接入约定

本文定义框架1.2.0可复用单任务入口与未来总调度器之间的契约。当前新增的是入口、
模板和相应测试，不是总调度器；现有正式业务入口、任务注册、生产运行及历史重建
均须另行接入验收。完整业务流程见[历史全量转每日增量标准流程](历史全量转每日增量标准流程.md)。

## 1. 接入单元

每个任务目录自包含业务模块、README、`generation_spec.json`、测试、就绪判断、
独立校验和入口。任务目录使用与输出主题相同的小写英文名称。统一调度只调用明确
注册的入口，不扫描目录猜测哪些`.py`可以执行，不把公式挪入通用模块。

业务入口调用以下公开模块接口：

```python
run_task_cli(metric, *, check_ready, validate_output, argv=None) -> int
```

入口复用`MinuteConversionRunner`与`RunConfig`，不定义另一套全量/日更公式。
`check_ready(metric, config, dates)`核验本次输入，成功返回`None`，未就绪抛
`InputsNotReady`；其他返回值（包括`False`）视为错误，两个钩子只接收日期副本；
`validate_output(metric, config, dates)`返回字典，其成功条件是`status="passed"`、
`dates`精确覆盖请求ISO日期列表、`level`非空。独立业务公式及证据由任务提供，
协议只验证声明结构与覆盖，不能替业务证明公式或校验等级真实充分。

`scripts/run_task_template.py`使用已有`MinuteTradeVolume`示例；默认钩子未接入会
拒绝执行，不是正式成交量业务定义。接入业务必须替换为自己的已验收模块与钩子，
不能只改任务名称或让钩子无条件通过。

## 2. 命令行契约

| 参数 | 约定 |
|---|---|
| `--mode` | 必填，`full`、`daily`或`repair` |
| `--date` | ISO单日，与`--dates-file`二选一 |
| `--dates-file` | UTF-8 JSON ISO日期数组，与`--date`二选一 |
| `--input-root` | 必填，明确的输入根目录 |
| `--output-root` | 必填，指标父级类别目录，具体结果位于其指标子目录 |
| `--result-json` | 必填，每次唯一的新报告路径，不能在输入/输出子树或覆盖已有文件 |
| `--execute` | 显式执行；省略则仅生成`planned`计划 |
| `--date-workers` | 日期worker数，0表示框架自动建议，调度方仍须控制全局预算 |
| `--arrow-threads-per-worker` | 单worker Arrow线程上限 |
| `--auto-memory-fraction` | 自动并发的可用内存比例，不是多任务总预算 |

不提供隐式昨日、历史发现或全目录执行。`full/daily`使用resume，`repair`只覆盖
指定日期；不为绕过来源门禁自动切换repair。`daily`显式`[]`返回`no_work`且不读取
源；`full/repair`空集合是参数错误。`no_work`不是“全部历史验收通过”。

dryrun只核对参数及计划，不执行输入就绪、生成和业务校验，不因计划成功宣称来源
可用。调用方不能把dryrun提交为正式日更成功记录。

执行时在`output_root/metric/.task.lock`获取指标锁，防止兼容入口对同指标同时
写入。锁不保护绕过本入口的旧脚本，不是跨指标事务或跨任务资源锁。残留锁需人工
核对进程及任务记录后处理，入口不自动抢锁，也不自动kill进程。

## 3. JSON结果协议1

独立结果JSON文件是唯一机器接口。stdout/stderr允许包含日期子进程的业务日志，
调度方不得解析整串stdout或靠最后一行日志判成功。报告更新采用原子替换。

每次调用由入口产生独立`invocation_id`；它不等于生成执行器的`run_id`。调度方需
保存实际子进程、启动时间、argv、独立报告路径与该身份，禁止读取另一轮旧报告。
字段含义如下：

| 字段 | 含义 |
|---|---|
| `protocol_version` | 固定为1；未知版本须拒绝误判 |
| `invocation_id` | 本次入口调用唯一身份 |
| `mode` | 本次请求的运行模式 |
| `metric` | 实际指标名，须与注册表一致 |
| `requested_dates` | 规范化ISO日期列表，须与调度请求精确对账 |
| `status` | 执行中为`running`；终态为`planned`、`no_work`、`complete`、`failed`、`not_ready`或`locked` |
| `generation` | 执行器原始payload，未生成时为空；保留run_id、请求/跳过日期等证据 |
| `validation` | 业务校验器的结果，未校验时为空；成功须含status、dates、level |
| `error` | 失败或拒绝原因；无错误时为空 |
| `exit_code` | 入口约定退出码，须与实际子进程退出码一致 |

| 退出码 | 含义与调度动作 |
|---:|---|
| 0 | 可能为`planned`、`no_work`或`complete`，必须继续检查JSON状态 |
| 1 | 生成、来源或校验等失败，分类诊断，不盲目重试 |
| 2 | 参数、日期或报告路径错误，修正配置后再调用 |
| 3 | 输入`not_ready`，依据上游状态有界等待后重试 |
| 4 | `locked`，先核对同指标运行，不抢锁、不终止用户进程 |

参数解析或无法建立安全报告路径时可能无法得到有效JSON，调度方仍须以实际退出码
和报告缺失记录失败，不能要求入口为了报告而覆盖已有文件或写入输入/输出目录。
报告损坏、缺失、身份不符、状态与退出码冲突均不可认定成功。
运行中的报告`exit_code`及`finished_at`为空，不是成功检查点；进程被强制终止后
可能留下running报告或残留锁，须结合实际进程和任务账本恢复，不能补造成功结果。

非空正式请求只有顶层`complete`、`generation.status="complete"`、生成请求集合与
本次一致、`validation.status="passed"`且校验日期精确一致、等级满足注册要求，
并且实际退出码和`exit_code`均为0时，才可进入任务成功对账。`complete`不意味着
所有历史已经适配；外部仍须核对当前发布版本与本次所需证据。

## 4. 生成与校验范围

入口执行顺序是就绪检查→resume或repair生成→全部请求日期发布完成→校验全部
请求日期。resume跳过的日期仍需校验，支持“上次已生成但校验失败”的同范围重试。
每日不做交错校验，不把本次范围扩大成历史全量。

首次全量如需外部生成/校验交错，须另按
[交错并行校验要求](逐笔转分钟交错并行校验提示词.md)实现并验收。启动时旧manifest
不证明本轮run_id；月文件存在、暂存完成或日志完成不证明发布检查点已提交。异步
检查点可延迟整月，组内部分文件已替换也不代表每项凭证就绪，不补造生成凭证。

校验器固定文件快照，保存独立的版本化结论；输入、输出或算法变化时结论失效。
结构检查、样本独立复算和全量逐值复算是不同等级，调度方不能只看“passed”文字。
入口本身不提供动态校验队列、持久化校验断点或跨任务资源协调服务。

## 5. 未来显式任务注册表

未来总调度器应由人工维护显式注册项，至少包含：

- 稳定任务ID、绝对Python解释器路径、绝对cwd和入口脚本路径。
- 实际框架/业务模块导入位置及版本要求，指标名、输入根和输出根。
- 可信交易日与上游成功清单来源、依赖关系及业务截止时间。
- 本次显式日期集合/日期文件、唯一报告与日志路径、允许运行模式。
- 日期worker、Arrow线程、内存与I/O声明、并行互斥、校验最低等级及重试策略。

使用`subprocess`参数数组传递argv，并指定cwd，不拼接shell字符串，不通过递归
搜索运行所有Python文件。不同业务可能均使用`minute_metrics`包名，必须各自cwd
与独立子进程核对导入；不把多个同名业务包全局混装后在一个解释器里串行import。

示意注册项只能描述已验收入口，不能凭脚本文件存在自动认为其支持本协议。旧正式
入口是否迁移应逐项确认，不改它们不等于已经纳入统一日更。

## 6. 资源与并行

总调度器默认串行；需要并行时使用全局CPU、内存、Arrow线程及I/O预算约束的有界
队列。各任务内部日期进程与Arrow线程数须计入总预算，同时考虑输入读取、月文件
合并发布和独立校验的瞬时峰值。

不能让多个任务各按当前可用内存的70%独立自动扩张，再将其当作安全全局策略。
应预先划分预算，采用保守比例或明确worker上限，记录实测峰值后再调整。512G内存
和两张GPU不自动带来分钟CPU/I/O任务收益，不为用满机器而增加无收益的并行。
资源紧张时减少后续派发或等待，不擅自kill生成任务或用户进程。

首次大范围交错校验需共享全局预算，生成优先；不能把生成、校验、日期和Arrow
并行数简单相乘。本次单任务入口提供参数，但没有实现上述总调度资源仲裁。

## 7. 重试、漏日与修订

上游未就绪与业务失败分层处理：前者按有界等待、次数与超时策略重试，后者保留
错误证据并诊断。每次重试使用新报告路径，保留原请求集合和上一次结果，禁止扩大
到全部历史或自动从resume切换repair。

总账本按任务×指标×日期记录候选、等待上游、运行、生成已发布、校验通过、失败和
失效，汇总目标/通过/等待/失败数。与可信交易日及业务依赖对账，空任务应有原因；
“没有文件所以无任务”不能解释本应存在的交易日。日志不是总账本或发布凭证。

迟到新日期可在就绪后显式daily补入；已有日期修订、来源或算法变更须列明影响，
经授权repair并重新验收。源码和框架版本参与resume来源契约，1.2.0不能自动承接
1.1.0旧凭证；不迁移/伪造凭证，不自动重建历史。生产输出仍可能包含不同源码时期
的已保留日期，须逐日期如实记录，不能宣称整月或所有历史已升级。

## 8. 接入验收与本次边界

验收至少覆盖：参数与中文显示、dryrun不生成、空daily不读源、缺源not_ready、
公式失败、缺/多校验日期、无等级校验、来源改变拒绝resume、同范围校验失败重试、
月内增量与repair保留其他日期、锁冲突、报告不覆盖、一次全量与分批增量一致。
业务的独立参考公式、242轴、股票集合、NULL语义和来源发布证据仍需单独验收。

框架编译和测试通过，只证明相应代码范围。同步服务器代码也不等于正式业务接入、
历史结果重建或日更调度上线。本次不实现未来总调度器，不运行生产，不修改正式
业务入口和生产数据；涉及远程写入、取数、数据库或网络操作按AGENTS先说明并授权。
